# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An interactive tangram player: React + TypeScript (Vite) deployed as a Cloudflare Worker with static assets. It has two modes:
- **Free play:** arrange the 7 tans; save designs to localStorage; export PNG.
- **Puzzles:** fill one of 50 hand-authored silhouettes (`scripts/figures.ts`). `tangram_asset.jpg` is the user's original inspiration sheet; it isn't used by the code.

## Commands

```bash
npm run dev          # Vite dev server (runs the Worker in workerd via @cloudflare/vite-plugin)
npm run build        # tsc -b (app + worker projects) then vite build → dist/client + dist/tangram
npm test             # vitest run (all src/**/*.test.ts)
npx vitest run -t "push physics"   # run a single describe/test by name
npm run puzzles      # rebuild src/data/puzzles.json from scripts/figures.ts + write scripts/out/preview.png
npm run deploy       # build + wrangler deploy: normally done by CI from main, see below
npm run analytics    # gameplay report from production D1 (-- --days 7, -- --local)
```

Vitest uses its own `vitest.config.ts` on purpose. Loading `vite.config.ts` pulls in the Cloudflare plugin, which fails under vitest with "There is already a server associated with the config".

## CI / deploy (`.github/workflows/`)

- **`ci.yml`** runs on every PR and on pushes to `main`, in this order:
  1. `npm test`
  2. `npm run build` (typecheck + build)
  3. a puzzles check: `npm run puzzles`, then `git diff --exit-code src/data/puzzles.json`.
- If you edit `scripts/figures.ts`, run `npm run puzzles` and commit the regenerated JSON, or CI fails.
- **`deploy.yml`** runs on every push to `main` (and manually via workflow_dispatch). It tests, applies D1 migrations (`wrangler d1 migrations apply DB --remote`), then runs `npm run deploy` with the `CLOUDFLARE_API_TOKEN` / `CLOUDFLARE_ACCOUNT_ID` repo secrets. The token needs **Workers Scripts: Edit** and **D1: Edit**.
- **Production follows `main`.** Don't run `npm run deploy` from feature branches; it overwrites the live Worker until the next merge.

## Architecture

**Units and coordinates.** Everything is in "tan units": a small triangle has legs of 1, so the 7 pieces total area 8. The board is an SVG whose `viewBox` is the board size in tan units. Pointer positions are converted with `getScreenCTM().inverse()`, and screen px per unit comes from `getScreenCTM().a`, because the viewBox is letterboxed inside the element.

**Responsive layouts** (`src/game/layout.ts`). There is no visible board: the SVG fills the `.stage` element and pieces sit directly on the page backdrop.
- `useFitLayout(ref, figure?)` in `App.tsx` measures the stage, then calls `fitLayout(w, h, figure)`.
- **The board is sized per puzzle.** `needs()` computes the smallest board that fits *that* silhouette (`figureExtent()`) plus the starting tray (`trayExtent()`, the square exploded by `TRAY_SPREAD`):
  - `GAP` between silhouette and tray, `MARGIN` around everything;
  - `SLACK` along the axis pieces travel, `CROSS_SLACK` across it.
  - Free play uses `FREE_MIN`.
- `fitLayout` then picks landscape (silhouette left, tray right) or portrait (silhouette top, tray below), whichever gives bigger pieces, capped at `MAX_UNIT_PX`.
- `makeLayout` centres the silhouette and tray together.
- **Small figures get big pieces; wide ones are limited by the screen.** The Dog is 8 units wide, so on a ~345px phone it can't exceed ~43px per unit.
- **Playability tests:** the `board fits each puzzle` tests check every puzzle on six screen sizes:
  - the silhouette and the tray fit, without overlapping;
  - the tray pieces start apart;
  - every piece can be turned in the tray and placed into the solution.
  Run them after touching any of these constants.
- Pieces are created only once the layout is known; `usePieces` starts with `null`.
- On every resize, `remap()` moves each piece by its offset from the nearest anchor (silhouette or tray in puzzles, board centre in free play), so a half-built figure survives resizes and phone rotation. Saved designs store the `Layout` they were made on and are remapped when loaded.

**Piece model** (`src/geometry/pieces.ts`):
- Each piece's `shape` is its polygon in the classic 2√2 square layout, re-centered on its centroid. `rot: 0` therefore means "as in the square", and `squareLayout()` reproduces the solved square.
- `PieceState` is `{id, x, y, rot (degrees, [0, 360)), flipped}`. World polygons always come from `piecePolygon()`.
- The UI only produces 45° multiples: buttons and taps use `step45()`, and the twist gesture snaps to 45°. Free angles are representable but not used.
- Free-play designs saved before rotations were in degrees stored 45° steps (0..7). `loadDesigns()` migrates any design without `v: 2`.
- `flipped` mirrors the local shape before rotating. `piecePolygon()` reverses the vertex order then, so winding stays consistent.
- **Every piece is flippable.** `flip()` in `game/actions.ts` mirrors left↔right *on screen*, not along the piece's own axis. Since R(rot)·M = M·R(-rot), that means `rot → -rot` plus toggling `flipped`.
- Rendering doesn't use `piecePolygon()`. Each `<path>` draws the local `shape` with a CSS transform `translate · scaleX(sx) · rotate(deg)` from `pieceTransform()`, so rotate/flip/snap animate via CSS transitions. Transitions are switched off while dragging (`.board.is-dragging`).
- `useDisplayAngles` in `Board.tsx` keeps angles continuous, so 315°→0° animates the short way. A test checks that `pieceTransform` and `piecePolygon` agree; keep them in sync.

**No-overlap physics** (`src/physics/resolve.ts`). Pieces never overlap; dragging pushes pieces out of the way.
- `resolve()` runs iterative SAT separation (`mtv()` in `geometry/polygon.ts`; all tans are convex). One piece is held fixed, pieces it overlaps are pushed fully, and other pairs split the push. Pieces are clamped to the board.
- **Sticky groups:** `stickyGroups()` links pieces that share an edge into connected components, recomputed on every `resolve()` call.
  - "Share an edge" means `cornerJoints()` in `geometry/polygon.ts`: a flush, parallel stretch (`sharedEdges()`, within `STICK_TOL`, overlapping ≥ `STICK_MIN_LENGTH`) where **at least one end is a corner of both pieces**. That's the user's rule: together the pieces must form a clean new corner or a continued edge.
  - Pieces slid partway along each other, or touching only at a corner or tip, do **not** join.
  - Outline locking (`isLocked`) deliberately still uses plain `sharedEdges()`, because a correctly placed piece can sit mid-way along the silhouette's border.
  - Collisions shift a whole group rigidly, and board clamping is per group, so bumping a built figure never breaks it apart.
- **Pulling into exact spots** (`slotSnap` in `check.ts`): `PuzzlePlay` passes `slots`, the puzzle's `solution` placed on the outline, to `Board` and `usePieces`.
  - After every drop, finished dial or twist (`snapAfter` in `Board`), and after rotate/flip (`usePieces`), a piece with the **same outline** as a free spot within `SLOT_SNAP_DISTANCE` (0.25) moves exactly into it. The two identical large or small triangles are matched by geometry.
  - A group moves by one shared offset, and only if every member lands on a free spot.
  - It takes priority over the normal edge/vertex snap (`SNAP_DISTANCE` 0.2). This is what makes detailed outlines (e.g. the Fox) easy to align.
- **Locking to the outline:** in puzzles the physics board carries `outline`, the placed silhouette. `usePieces` builds `{ ...layout.board, outline }`.
  - `isLocked()`: a piece is locked when it sits inside the silhouette with an edge flush against its border.
  - `lockedIds()`: locked pieces plus everything joined to them.
  - Locked groups are walls in `resolve()`: never pushed or clamped. A move that would push one returns `null`, so the mover stops or slides.
  - Dragging a locked piece yourself still works, because moving pieces are excluded. Locked pieces get `.piece.locked`: slightly brighter, with a thin golden edge.
- **Performance:**
  - `resolve()` returns immediately when nothing overlaps; groups and locks are only computed once something collides.
  - `moveWithPush()` stops sub-stepping once a step makes no progress.
  - Keep both. Without them, pushing against a locked piece costs ~11 resolves × ~30 sub-steps per pointer move, and the page stalls.
- **`transformWithPush` (turn/flip/snap) never refuses just because the turned piece hits something immovable.** If neighbours can't be pushed (locked to the outline, or jammed), it retries with the turned piece itself nudged clear (`resolve(…, [], board, ids)`).
- `resolve` never returns overlapping pieces.
- **What moves:** `resolve(pieces, fixed)`, `moveWithPush(pieces, ids, …)` and `transformWithPush(pieces, states[])` all accept several pieces, which then move as one rigid body. Those `fixed` pieces are excluded from grouping during the move, so nothing new latches onto the body mid-drag.
- `resolve()` returns `null` when it can't settle, e.g. pieces jammed against a wall.
- `moveWithPush()` subdivides a drag into ≤0.2-unit steps so pieces can't tunnel. Each step tries the direct move, then axis-aligned slides, then bisects toward the furthest valid point.
- **Drags go through `dragTo()`, which forgives an imprecise hand.** It runs `moveWithPush()` first. If that is blocked short of the finger (a locked neighbour, or a gap only just wide enough), `fitAt()` puts the dragged pieces right at the finger and nudges them up to `FIT_NUDGE` (0.3) out of everything else, which stays put. Whichever ends closer to the finger wins.
  - Without it a snug spot can only be entered along a perfect path: a hair of wobble catches a neighbour's corner and the piece stops at the entrance. A test drags the last piece of every puzzle in along a wobbly path; plain `moveWithPush` finished 92/342 from the tray and 207/266 on a short approach, `dragTo` finishes all of them with no overlaps at any step (`src/fit.test.ts`).
  - A side effect: a piece can hop over a locked figure to a free spot under the finger, which keeps the piece under the finger rather than stuck behind the figure.
- `transformWithPush()` is used for rotate/flip/snap; a `null` result means the action is rejected.
- Touching (overlap ≤ `EPS`) is not a collision. That is what lets snapped pieces sit flush.

**Snapping** (`src/geometry/snap.ts`). On drop, `findSnap()` picks the smallest offset within `SNAP_DISTANCE`:
- Vertex↔vertex matches are preferred over vertex↔edge projections.
- Targets are the other pieces plus the puzzle silhouette ("guides").
- A candidate is skipped if it would create an overlap.
- The UI wiring is in `game/actions.ts` and `components/Board.tsx` (`onUp`).

**Solve detection** (`src/game/check.ts`). `coverage()` is a grid-sampled IoU (even-odd point-in-polygon) between the pieces and the silhouette. The sample grid is offset by odd fractions (`OFF_X`/`OFF_Y`) so samples never land exactly on the integer-coordinate edges shared by two pieces. `evaluate()` returns two things:
- the **in-place** match, shown as "Match %";
- `solved`, which is true when either the in-place IoU or the **centroid-aligned** IoU reaches `SOLVE_THRESHOLD`, so a figure built anywhere on the board counts.

Any arrangement whose shape matches the silhouette wins.

**On solve, pieces click into place** (`perfectFit` in `check.ts`, called from `PuzzlePlay`'s check), so the finished figure, and its exported image, is a gap-free 100%:
- **Matching:** each piece goes to the nearest slot in the puzzle's stored `solution` with the same kind *and the same outline*, within `MAX_FIT_DISTANCE`.
  - Compare geometry, not `rot`. The two large (and two small) triangles have different base orientations, so equal outlines can have different `rot` values. A piece keeps its own rot/flip and only moves.
- **Where the figure ends up:** pieces are matched against slots around their own centre (wherever the figure was built), then the result is placed **on the drawn silhouette** (`outlineAt` = `layout.target`). A figure finished anywhere glides onto the outline, so exports are always framed on it. `.piece.solved` has a longer transform transition for this move.
- **Alternative solutions:** if the arrangement doesn't match the stored solution, `centreOn` moves the whole figure onto the outline, then **`fitToOutline`** locks it edge to edge.
  - Every piece corner is pulled to the nearest outline corner or neighbouring corner (failing that, the nearest outline or piece edge), within `FIT_REACH`.
  - All pieces relax together by translation only, anchored by the fixed outline, until corners meet.
  - The result is accepted only if it matches the outline (>99.5%) with no overlaps; otherwise `settleFlush` is the last resort.
  - The meter shows 100% only when the figure really locked.
  - Tests: every puzzle knocked loose and refitted without its solution, plus a genuinely different Square solution.
- **Animation:** the CSS transform transition makes the pieces glide in.

**Puzzle authoring** (`scripts/figures.ts` → `scripts/build-puzzles.ts` → `src/data/puzzles.json`):
- **Authoring:** each figure lists its 7 pieces as exact polygons. Use helpers rather than hand-typing coordinates:
  - `tri` (right angle, legs in a direction), `sq`, `para`, `raw`, plus `go(p, deg, len)`, which is exact for 45° multiples;
  - sub-assemblies `smallSquare()` (2×2 square), `strip()` (4×1), `roof()` (two large triangles) and `classicSmall()`.
- **Validation** (`npm run puzzles`), per figure:
  - every polygon must be congruent to a real piece; it is matched to an id, rotation and flip;
  - all 7 pieces must be used, with no overlaps, and they must be connected.
  - Errors are printed and the JSON is not written.
- **Outline:** the silhouette is built by edge cancellation (`outline()`): weld vertices, split edges at T-junctions, cancel shared segments, then chain the rest into loops. Don't swap in a polygon-clipping union; √2 rounding leaves seams along partially shared edges.
- **Loops:** multiple loops are normal. They come from holes or pieces touching at a single point, and are rendered and scored with even-odd.
- **Output:** each puzzle has `category`, `polygons` (centred on the figure's centroid) and the authored `solution`.
- **Tests:** the `puzzles` tests check every stored solution covers its outline at >99%.
- **Checking new figures:** always look at `scripts/out/preview.png` after adding one.
- **Keep ids stable:** puzzle ids (`p01`…) come from array order, and saved progress (`tangram.solved`) is keyed by id. So add new figures **at the end** (`MORE_FIGURES`), never in the middle. Categories group them in the picker regardless of order.
- **Composition helpers:** `rot45` (turn a figure 45°) and `square2` (the two large triangles as a 2×2 square) join the sub-assemblies above.

**Image export** (`src/exportImage.ts`, `exportBoardImage`):
- Both modes export the board through this module.
- **What it renders:** it clones the live SVG and strips UI-only overlays (`UI_ONLY`: joints, rotation ring, buttons, flashes, group outline). Styles that live in CSS (pieces, `.guide`) are re-applied as attributes, because a standalone SVG image doesn't get the page's stylesheet. It paints a rich backdrop (`paintBackdrop`: gradient, colour glows, dot texture, vignette) and an optional caption. Pieces get **no shadows**, because a piece's shadow falls on its neighbours as dark bands along inner edges.
- **No light outlines in pictures or on a solved figure:** pieces get a hair-thin stroke in their *own* fill colour, which hides anti-aliasing seams without drawing a line. On screen this is an inline `stroke` style plus `.piece.solved`, because inline style beats the stylesheet's `.piece` stroke.
- **Resolution:** it rasterises at ≥ `PX_PER_UNIT` px/unit and a long side ≥ `MIN_LONG_SIDE`, capped by `MAX_LONG_SIDE` / `MAX_PIXELS`. The caps exist because iOS Safari fails on huge canvases.
- **Format:** JPEG at `JPEG_QUALITY`, because PNG of the glow backdrop runs to several MB (≈4 MB versus ≈0.3 MB for the same 2048px image).
- **Free play** exports the whole board.
- **Puzzle mode** (toolbar **Export**, plus **Save image** on the solved card) crops to the silhouette and pieces, captioned "Solved in m:ss" or "In progress · N% matched".
- **Delivery:** on touch devices that can share files it opens the share sheet; otherwise it downloads.
- **Link and QR:** exports carry `link` (`puzzleLink(id)` for puzzles, `SITE_URL` for free play, both from `src/site.ts`). It's printed as a quiet address line, and as a small dark-on-white QR tile in the caption's right corner (`qrTile`), never over the figure.
  - The QR encoder (`qrcode-generator`) is imported dynamically, only when exporting.
  - Captions scale with big pictures (`captionScale`) so the QR stays scannable at phone size. It's verified to decode with zbar and OpenCV down to 700px wide.
  - With a link, narrow crops are widened to `minWidthWithLink`.
- **Deep links:** `?p=<id>` opens a puzzle directly (`puzzleIdFromUrl`). `App` keeps the address in sync with `history.replaceState`, so the current puzzle can be shared by copying the URL.
- If you add a new overlay to `Board`, add its class to `UI_ONLY`.

**Progress & badges** (`src/storage.ts`, `src/game/badges.ts`, `src/components/Badges.tsx`):
- **Progress v2** (`tangram.progress`): `{ v: 2, solved: { [id]: { best: ms, first: "YYYY-MM-DD" } }, designsSaved, exports }`.
  - `loadProgress()` migrates the old `tangram.solved` (`{id: bestMs}`) once, with today as `first`.
  - Change it only via `recordSolve` / `bump`.
  - `App` holds it in `updateProgress` (with a ref, so a badge toast fires once even under StrictMode).
- **Badges:** `computeBadges(progress, puzzles)` evaluates 12 pure rules: first solve, each category, all puzzles (the count is dynamic, so new puzzles raise the bar), speed, distinct days, design saved, picture exported.
  - `newlyEarned(before, after)` drives the unlock toast (`BadgeToast`). The header chip opens `BadgesSheet`.
  - Hints never name a specific puzzle.
  - The rules are pure, so the planned D1 backend can reuse them.
- **Picker:** category headers show `n/total` with a meter. The wordmark hides ≤430px so the badge chip fits.

**State/UI** (`src/App.tsx`). The `usePieces` hook owns piece state, the selection, and the rotate/flip commands, and handles layout remapping. It returns `boardProps` to spread onto `<Board>`. `Board` reports live drag updates via `onChange` and finished moves via `onSettle`; puzzle mode runs `evaluate()` in `onSettle`. Persistence is localStorage (`src/storage.ts`): designs, deleted-design markers, progress v2 (see Progress & badges), tip flags. Optional cloud sync on top of it is described under Accounts & sync.

**Interaction model** (designed for touch first). The selection is a `string[]`: one piece, or a whole joined group.
- Pressing a **piece** moves only that piece, pulling it out of its group.
- Pressing a **joint** moves the whole group. Joints are the glowing lines `findJoints()` draws on every shared edge; each has an invisible `.joint-hit` line, `JOINT_HIT_PX` wide on screen, to grab. Hovering a joint highlights the group, and tapping one selects the group.
- Rotate, flip and twist work on the selection: `rotate`, `flip` and `turnBy` in `game/actions.ts`. For a group they turn or mirror about the group centroid via `turnGroup()`.
- Snapping on drop uses all moving pieces (`findSnap(pieces, ids, guides)`).
- While moving there's no selection border. The floating controls follow the moving piece on desktop, faded and inert (`.piece-actions.moving`); on touch they hide until the drop.
- `JointTip` shows a one-time explanation over the board; the flag is stored in localStorage under `tangram.tip.joints`.
- Pressing a piece selects it and starts a drag. Movement under `TAP_PX` screen px is a tap.
- Tapping an *already-selected* piece rotates it 45°. The first tap only selects; `Drag.wasSelected` is captured at pointer-down.
- **Two-finger twist:** only fingers inside the selection's **zone** count. The zone is a circle around the selection with margin `ZONE_MARGIN` (`zoneOf` / `inZone`), shown as a faint `.twist-zone` ring on touch screens.
  - **Drag + twist** (`Twist`): one finger drags the piece and a second lands in the zone; the angle between them rotates in 45° steps.
  - **Free twist** (`FreeTwist`): a finger landing on empty space inside the zone becomes `pending`. If a second finger lands in the zone, on a piece or not, both fingers rotate the selection in place. Lifting either finger ends it, then snaps and settles.
  - **One-finger dial** (`Dial`): if the pending finger moves ≥ `TAP_PX` before a second one arrives, it becomes a joystick-style dial. The selection turns in 45° steps to follow the finger's angle around the zone centre, ignoring the `DIAL_DEAD_ZONE` near the centre. No touch marker is drawn; only the ring highlights. Works with a mouse too.
  - A pending finger lifted quickly counts as a tap on empty space and clears the selection.
  - **The floating buttons** sit inside the ring, so they start a `pending` too (`onButtonDown`). A tap presses the button, and moving from one starts the dial.
  - `secondFinger()` routes any extra finger to the active gesture instead of starting a competing one.
- The selected piece gets floating ↺ ↻ ⇋ buttons (`PieceActions`), sized in screen px (`BUTTON_PX`) so they stay thumb-sized on phones. They are placed above the piece, or below if there's no room.
- The same actions are in the `Toolbar` and on the keys `R` / `Shift+R` (or `E`) / `F` / `Esc`.
- A snap triggers a short vibration (`navigator.vibrate`) and an orange flash at the contact point.

**Visual design** (`src/styles.css`):
- The theme is dark violet. `body` carries the gradient and dot-grid backdrop (`background-attachment: fixed`), and nothing frames the play area.
- Piece colours live in `PIECES` (`geometry/pieces.ts`) and are reused by the logo, the confetti and the picker card accents. `Board` turns each colour into a glossy `linearGradient` (`#tan-<id>`, via `mix()`).
- Buttons are translucent "glass" (`--glass*` variables); primary actions use the `--hot` gradient.
- The silhouette is a translucent fill with a dashed outline. Once solved, the figure pulses with a glow (`.pieces.solved-figure`) and `Confetti` plays.
- SVG `filter: drop-shadow(...)` lengths on pieces are in board units, not screen px, so they are tiny values like `0.1px`.
- **No spilling effects on resting pieces.** A drop shadow or outer glow on one piece paints over its neighbour along a shared edge, so two pieces meeting edge to edge look like one overlaps the other. So:
  - resting pieces have no shadow (only `.lifted`, while dragging);
  - joints are a fine line with no glow;
  - `.piece.locked` uses brightness plus a thin stroke;
  - the solved glow is on the whole figure (`.pieces.solved-figure` wraps the piece paths), not on each piece.
- `prefers-reduced-motion` disables the animations.

**Mobile CSS** (`src/styles.css`):
- While playing, `.app.playing` is exactly `100dvh` and the board stage gets the leftover height.
- At ≤600px wide, the toolbar becomes equal-width 46px buttons and the footer is hidden.
- On short landscape screens (`max-height: 520px`), the toolbar becomes a vertical rail beside the board.
- The board has `touch-action: none`. The design-name input uses `font-size: 16px` to stop iOS from zooming into it.

**Worker** (`worker/index.ts`, `wrangler.jsonc`). Assets are served as an SPA (`not_found_handling: "single-page-application"`). Only `/api/*` reaches the Worker code (`run_worker_first`).

**Accounts & sync** (anonymous, no OAuth, no email):
- **Identity:** a random sync code `TAN-XXXXX-XXXXX` (10 chars from a 31-char alphabet without 0/O/1/I/L). The D1 `players` table stores only its SHA-256, so the code is the only key. `shared/progress.ts` has `generateCode`, `normalizeCode` (accepts lower case, spaces, missing dashes) and `formatCode`.
- **`shared/`** is compiled into both the app and the Worker (both tsconfigs include it). It holds the `Progress` model, `mergeProgress` / `mergeDesigns` / `mergePayload` and `validatePayload`.
  - Merge rules: min best time, earliest first day, max counters; designs keyed by name, latest `savedAt` wins. A deleted design is a marker with `data: null`, so it doesn't come back from another device.
  - Merges are commutative and idempotent, so devices converge whatever order they sync in.
  - `validatePayload` drops entries that don't fit `LIMITS` instead of failing the whole sync, and clamps solve times to a day.
- **D1** (binding `DB`, schema in `migrations/`): `players`, `solves`, `designs`, `counters`. Add schema changes as new numbered migration files; never edit an applied one. Locally: `npx wrangler d1 migrations apply DB --local` (state in `.wrangler/`).
- **API:**
  - `POST /api/player` returns a new code (rate-limited by `CREATE_LIMIT`, 5/min per IP).
  - `GET` / `PUT /api/progress` and `DELETE /api/player` take `Authorization: Bearer <code>`; unknown codes get 401.
  - `PUT` merges server-side, writes only changed rows (with `min`/`max` upserts so concurrent syncs still converge) and returns the merged payload.
  - Every API request counts against `API_LIMIT` (60/min per IP); bodies over `LIMITS.maxBodyBytes` are refused.
- **Client (`src/sync.ts`), offline-first:** localStorage stays the source of truth and failures are silent.
  - No account until it's worth one: the first solve or saved design (`scheduleSync(true)`, debounced). Plain visits create nothing.
  - Syncs on load and after solves, saves, deletes and exports. All server calls go through `serial()`, so they never interleave.
  - Results are merged again with local state before saving, then `SYNC_EVENT` tells `App` and `FreePlay` to reload.
  - A 401 means the account was deleted elsewhere: the code is forgotten and local data kept.
- **UI** (`SyncPanel` in `components/Badges.tsx`, at the bottom of the badges sheet): the code with Copy and a QR; "I have a code from another device"; "Delete my online data" (two-step; sets `off` so no new account is created until "Turn sync back on").
  - The QR encodes `SITE_URL/#sync=<code>`. A fragment, so the code never reaches server logs. `codeFromUrl()` reads it once, strips it, and opens the sheet with the code ready to use.
  - Using another code uploads this device's progress into that account, then deletes this device's old account.

**Nickname** (`components/Nickname.tsx`, `game/names.ts`, `cleanNickname` in `shared/progress.ts`):
- **First visit:** `NicknamePrompt` asks for a name, with a random "Adjective Animal" suggestion as the placeholder (🎲 rolls another). Leaving it blank, or Esc, keeps the suggestion, so the prompt never returns. It's skipped when arriving with a `#sync=` code, since the account brings its own name.
- **Changing it:** the `NicknameRow` at the top of the badges sheet.
- **Rules (`cleanNickname`, applied on both client and server):** 1–20 characters; letters and marks in any script, digits, spaces and `._'-`; invisible and control characters are removed; a short blocked-word list is matched with spaces and punctuation squashed out.
- **Stored** as `tangram.nickname` = `{ name, at }` and synced in the progress payload (`players.nickname`, `nickname_at`). The latest `at` wins. A typed name gets `Date.now()`, an untouched suggestion gets `at: 0`, so a random name on a new device never overwrites a chosen one; ties go to the smaller name so both sides agree.
- **Where it shows:** export captions ("Solved by Aung in 0:42", "Made by Aung in free play"). It is never shown to other players.

**First-run tutorial** (`game/tutorial.ts`, `components/Coach.tsx`, the `tutorial` prop of `PuzzlePlay`):
- **Who gets it:** first visit, after the nickname prompt, unless the player arrives with a `#sync=` code, picks "Played before? Use your sync code" in the prompt, or already has solves. `tangram.tutorial` marks it done (finished or skipped). "How to play" in the picker replays it.
- **The lesson:** the Square (`tutorialPuzzle`) turned a quarter so both open spots face the tray. Five pieces start in place (`PLACED`); the medium triangle starts turned and the parallelogram mirrored (`tutorialStart`), so finishing needs a drag, a turn and a flip.
  - In the usual orientation the parallelogram's spot opens downward, and once the triangle is in, a straight drag from the tray gets stuck against it. Tests check both spots are reachable by straight drags in either order on five screen sizes.
- **Steps** (`STEPS`): goal ("Got it"), drag, turn, flip, finish. `stepDone` compares the pieces with how the lesson started, so steps done early are skipped. The current target pieces pulse (`hint` prop on `Board`, `.piece.hint`: a stroke inside the piece, nothing spills).
- The coach card sits above the stage (in the flow, not over the board). Leaving by ←, the mode switch or "Skip tutorial" ends it. The finish card explains joints and offers "Start playing" or "Free play".
- The finished lesson doesn't count as solving the Square (no `onSolved`), and Export is hidden. Analytics log `tutorial_start`, `tutorial_done` and `tutorial_skip` instead of puzzle events.

**Global stats** (`GET /api/stats`, `useGlobalStats` in `PuzzlePicker.tsx`):
- Per puzzle: synced solvers and the average best time (each time capped at `AVG_CAP_MS`, 10 min, so a forgotten tab doesn't skew it). Cards show "12 solved · avg 1:35".
- Only puzzles with ≥ `MIN_SOLVERS` (5) are returned, so no single player's time can be read off a card.
- Cached at the edge for `STATS_TTL` (5 min) with the Cache API; it is served before the rate limiter. Offline, cards just show nothing.

**Gameplay analytics** (`src/analytics.ts`, `POST /api/event`, `scripts/analytics.ts`):
- **Anonymous daily counters only:** each event bumps a row in `daily_events` keyed by (UTC day, event, puzzle). No player id, IP, device or cookie is stored, and nothing is sent when the browser has Do Not Track or Global Privacy Control on.
- **Events** (`EVENTS`, validated by `validateEvent`): `start`, `solve` (with time), `quit` (time and best match %), `export`, `design_save`, `free_open`. Times are capped at an hour.
- **Puzzle sessions** (`session` ref in `PuzzlePlay`): one `start`, then either a `solve` or a `quit`. A quit is leaving the puzzle unsolved or closing the page (`pagehide`). Unmount quits are deferred a tick so StrictMode's dev remount doesn't count.
- Sent with `navigator.sendBeacon` (falls back to `fetch` with `keepalive`); failures are ignored.
- **Visitors** (page views, referrers, countries, devices) come from Cloudflare Web Analytics: the cookie-free beacon at the end of `index.html` (its token is public). See the Cloudflare dashboard → Analytics & Logs → Web Analytics.
- **Reading it:** `npm run analytics` prints totals, per-puzzle solve rate / average time / where people give up (hardest first), and a per-day table.
